# Chaos contract for the simulated Kestrike

Read this guide before you read, change or validate a file under `chaos/`, or report
what a chaos campaign on the simulated Kestrike shows. Read
[the simulation guide](simulation.md) before you run a sweep for the contract.

## What the contract is

The chaos contract states what a chaos campaign on the simulated Kestrike may
claim. Its copy is Kestrike as the archived simulation worker runs it under
`campaign`, so every result is evidence about the simulation. A verdict is a judge's
exit code on recorded evidence: 0 held, 1 broken, 2 invalid, 3 incomplete. An
invariant enters the ledger only with the place where its property is agreed, as
[An agreed property](simulation.md#an-agreed-property) lists them, and with a judge, an
oracle outside the code under test, a witness and a control. The contract follows the
skill `chaos-enrollment` of plugin `chaos-testing`, and
[#297](https://github.com/ahrav/kestrike/issues/297) specifies it.

## Words

| Skill word | In this repository |
|---|---|
| copy, build | Kestrike as the archived simulation worker runs it under `campaign`; the archive's build digest |
| chaos scenario | one profile set at one count set, swept under stated bounds: a scenario row of `chaos/ledger.json` |
| run | one harness invocation: one `campaign sweep` of a new root under its own campaign name, then `sweep-status`, `confirm`, `findings`; kept under the run directory of the contract |
| evidence | the harness's copies from the root (sweep-status.json, suspects.jsonl, findings.json) and its own history.jsonl and run.json |
| judge | a script under the contract's judge directory that reads the evidence and its rows and exits 0 held, 1 broken, 2 invalid, 3 incomplete |
| chaos receipt | the judge's record for one row of one run, named by the run id and the row; not a CI lane receipt of `scripts/verify-receipts.py` |
| fence | a boundary of the worker's credentials or of the harness, with a probe and its refusal receipt |
| witness, control | a live run in which the check ran on real data; a run of an existing planted control or failing history, or the scenario's own sweep under a control build that the row's `control.how` states, its defect recorded as a label |

A chaos point is an existing `chaos!` point of `crates/kestrike/src/sim/chaos.rs`.
"Chaos contract", "chaos scenario" and "chaos loop" belong to `chaos/`.

and one receipt directory for each run beside the fence receipts. A receipt directory
holds receipts only. Whoever changes a ledger row a recorded run was judged against, a
judge file or a harness file records the runs under `chaos/tests/` again in the same
change, as that README describes. The contract's own runs under `chaos/runs/` and the

then `; ` and the sentence that no production figure applies; the harness reads the
profile list from it. The numbers beside it in `load` give the load multiple, 1, and
the sweep's workers, its batch seconds and its `--for` seconds.

## Validate the contract

Run the pinned validator from the repository root, in python3's isolated mode:

```sh
python3 -I chaos/tools/validate_contract.py chaos/ledger.json --root . \
  --project chaos/project.yaml --receipts chaos/receipts
```

With `-I`, the module path leaves out the script's directory and the user's site
directory, and the `PYTHON*` variables have no effect. The validator's imports then
come from the interpreter's installation, and a file beside the validator stays
unread. The result is that of the pinned file, whose SHA-256 `chaos/tools/README.md`
checks.

It prints one finding a line as `<row>: <code>: <detail>` and exits 1, or prints
nothing and exits 0. Exit 2 means an input was unreadable, a flag lacks its
companion, or the check itself failed.
At M0-2 of #297 it exits 1 with exactly four findings: `witness-missing` and
`control-missing` for each of the two invariants, which M0-3 clears. From M0-3 on it
prints nothing and exits 0.
`chaos/tools/README.md` gives the commands that check the copy's SHA-256 against its
record and its bytes against the installed skill.

A fence probe runs with the installed skill's probe script, probe_fence.py, as
the identity the campaign runs as, and writes the fence's receipt. The script starts
the row's `probe.identity` and `probe.command` as written, with the campaign's
credentials, and removes the earlier receipt first. For the four credential fences
of the contract's base both strings start `python3 -I chaos/harness/reach.py` from the working tree. With
`-I`, that script's own imports come from the interpreter's installation: a file
beside the script, the user's site directory and the `PYTHON*` variables have no
effect on them. The commands the script starts, `id`, `aws` and `gh`, inherit the
environment, which `trusted_base` lists.

The fifth fence, `ks-run-keeps-earlier-runs`, is a boundary of the harness. It is
probed by the harness's dry-run form on an existing run id,
`python3 chaos/harness/run_scenario.py ks-upload-no-fault fences --dry-run`, with its
identity read without `-I` as `python3 chaos/harness/reach.py identity`. Both start without `-I`, so
the files beside the two scripts, the user's site directory and the `PYTHON*`
variables reach their imports. Probe this fence from a shell that sets no `PYTHON*`
variable, with `chaos/harness/` holding its tracked files alone.

Run the probe script only when both of these hold:

- both strings equal the row at the pull request's base, or at the freeze once one
  exists, and either start with `python3 -I chaos/harness/reach.py` or are the two
  strings of `ks-run-keeps-earlier-runs` given above;
- every tracked file under `chaos/harness/` equals that base or freeze, which this
  command shows by exit 0, with the commit as `<base>`:

```sh
git diff --quiet <base> -- chaos/harness/
```

A new or changed probe string, and a new or changed file under `chaos/harness/`, wait
for review of that exact revision before the probe script runs; the reviewed commit
then serves as `<base>`. This rule binds an operator, and a deliberate edit by the
same identity stays the reach that `trusted_base` lists:

```sh
python3 <skill-dir>/scripts/probe_fence.py chaos/ledger.json <fence-id>
```

Exit 0 means refused with the expected text, and only then does the fence stand.
On any other exit, stop that step and ask the workstream's lead. A receipt records
no digest of `chaos/harness/reach.py`, so a change to that file or to a fence row is
reviewed first. Then every fence's probe runs again at the reviewed commit, and the
new receipts land in a commit that leaves `chaos/harness/` and the probe strings as
reviewed. Between the two commits the validator also reports `stale-probe` for each
fence whose strings changed.

## The readiness claim

Render the readiness claim from the ledger, the project file and the receipts, and
check that the committed claim is the one they render:

```sh
(
  test -d chaos && test ! -L chaos || exit 1
  new=$(mktemp chaos/.READINESS.XXXXXX) || exit 1
  trap 'rm -f -- "$new"' EXIT
  python3 -I chaos/tools/validate_contract.py chaos/ledger.json --root . \
    --project chaos/project.yaml --receipts chaos/receipts --claim > "$new" \
    && chmod 644 "$new" && mv -T -- "$new" chaos/READINESS.md
)
python3 -I chaos/tools/validate_contract.py chaos/ledger.json --root . \
  --project chaos/project.yaml --receipts chaos/receipts --check-claim chaos/READINESS.md
```

The first command writes the claim to a new file that `mktemp` creates in `chaos/`
and, only when the validator exits 0, replaces the claim entry itself with it
(`mv -T`); a directory at `chaos/READINESS.md` makes the render fail. A render that finds a problem prints its findings, exits
nonzero and leaves the committed claim as it was. The second command prints nothing for a current
claim. The pre-push hook's tool `pre-push-checks` runs it as
[the pre-push checks](ci.md#pre-push-checks) describe.

A `row-changed-after-run` or `stale-receipt` finding stays after a new render: a
receipt names a ledger row, an evidence file, a judge or a harness file that changed
after its run. Restore what changed, or retire the old run with the owner and make new
runs and receipts, then render again. An edit under `frozen_paths` waits for the owner
first, as `chaos/approval-policy.md` says.

The receipt of a run records the SHA-256 of each file under `chaos/harness/`, of each
judge file and of each ledger row it names. Before you make a run whose receipt is to
merge, merge the destination branch into the branch that makes the run, so that a
later merge changes none of them. The check is the second command above at the merged
tip: it prints nothing.

The pre-push hook refuses a receipt or run record that holds 12 digits in a row, or
three groups of 4 joined by `-`, with no letter or digit beside them, since that is the
form of an AWS account number. A run id, the roots directory and the archive path end
up in the run record, so keep each digit group in them shorter: write a timestamp with
a separator, as in `20261123-2207`.

## Statuses

A committed scenario status is `open` or `broken`. `held` needs the build digest,
which changes with each merge, so a hold lives in the loop's log. The validator reads
the ledger only at `chaos/ledger.json` inside `--root`, and `--freeze-commit` needs the
freeze commit in that root's git history. So a hold is checked in a scratch checkout
outside this one, made with `git worktree add --detach <dir>` and given the current
`chaos/` tree of this checkout, runs and receipts included. There the coordinator sets
`held` in `chaos/ledger.json`, or `fixed` for a scenario that broke at an earlier build,
and runs the contract check from the scratch root with `--root .`, `--build` and
`--freeze-commit`. The hold is logged with the check's exit, its build digest and the run ids only when
that check exits 0 and prints no finding; any other result logs no hold. A logged hold counts only for the
build it names. Where the run rules read `held` or `fixed` from the ledger, to pick the
next scenario or to decide the end, the coordinator runs that check again at the build on
the copy and counts the hold only when it passes again. The committed ledger and the
claim keep `open` or `broken`. A scenario is
`broken` when a live run broke one of its invariants, and its receipt then holds the
full rule text. A sweep counts toward a hold only with `profiles.<profile>.replays`
above zero for each of the scenario's profiles (#297, "Verdict mapping"), and with no
suspect of class `replay differs` anywhere in its own record, a control or a history
the sweep ran beside the scenario's profiles included (#297, R24).

After the freeze a status of `held` or `fixed` is set as a record: a pull request's
first lines and its entry in the loop's log give the contract check's exit with the
freeze id, the build and the run ids, run in an uncommitted copy of the tree that
carries the status, and its merge into `main` puts that record on `main` and sets the
status. No commit carries `held` or `fixed` in `chaos/ledger.json`, on a branch or on
`main`: with either in the committed ledger, the contract check as the pre-push check
runs it, without `--build` and `--freeze-commit`, prints `build-unchecked` and
`freeze-unchecked` for the row and exits 1 (`chaos/approval-policy.md`, "Who runs
it"; `chaos/interview.md`, OQ-1 under "Ruled for the owner").

## Run a scenario

A run is one harness invocation. The harness takes the profile set, the workers, the
batch, `--for` and the deadline from the scenario row, sweeps one new root under the run
id as campaign name, copies the evidence into `chaos/runs/<run-id>/` and runs the judges
of the scenario row and of each invariant it lists. Build the archive from a clean
checkout, since the build record names the revision and whether the tree was dirty:

```sh
CARGO_PROFILE_DEV_OPT_LEVEL=3 campaign sim archive --output <archive>
```

The sweep needs a delegated cgroup, as
[Host requirements](../../crates/campaign-supervisor/README.md#host-requirements)
describes. Save this wrapper outside the checkout, with the paths of the checkout, the
archive, the `campaign` binary and the roots directory filled in. The roots directory and
the archive stand under `/data/tsw/campaigns` on this host:

```sh
#!/bin/bash
set -euo pipefail
D=/sys/fs/cgroup$(cut -d: -f3 /proc/self/cgroup)
mkdir -p "$D/controller"
echo $$ > "$D/controller/cgroup.procs"
echo '+cpu +memory +pids' > "$D/cgroup.subtree_control"
mkdir -p "$D/campaign"
export CAMPAIGN_CGROUP_ROOT="$D/campaign"
cd <checkout>
exec python3 chaos/harness/run_scenario.py "$@" \
  --archive <archive> --campaign <campaign binary> --roots <roots directory>
```

A scenario run starts on a worker that the session's workstream alone uses, after the
session's fence check: A1 of `chaos/interview.md`, who else uses the worker and
`/data/tsw/campaigns`, and when, is answered on the owner's behalf for such workers
(`chaos/approval-policy.md`, "Ships without asking"). On any other host, the one on
which the owner runs the loop afterwards included, start no sweep until
`chaos/interview.md` records the owner's answer for that host. While "Open for the
owner" there lists that part of A1, ask the owner or the workstream's lead for the
answer, and go on with work that runs no scenario. Building the archive and the
harness's `--dry-run` start no sweep.

The rehearsal's sweeps started before `chaos/interview.md` held that answer, on #297's
milestones and the workstream lead's decisions. A1 of that file records which sweeps
and on what footing. The thirteen sweeps of 25 November 2026 (eleven runs made again,
one run of an earlier series and one fixture) also started before the file held it, on
the workstream lead's statement that the question was answered on the owner's behalf.
The ruling entered the file later that day, and A1 keeps the record of that order. The
rule above holds for every later sweep, a run of record made again included.

Before the first run of a session, before any run on a worker other than the one the
fence receipts under `chaos/receipts/fences/` name, and once in every 24 hours of a
session, the fences are checked in this order. First run the contract check. When it names
a fence `probe-not-refused`, keep that receipt as it is, start no run, and ask the owner
or the workstream's lead. Otherwise record again the probe of each fence that meets both
conditions of "Validate the contract", with the probe command there, since the probe
replaces the fence's receipt. While their strings equal the row at the base or the freeze,
all five fences meet the first condition: the four credential fences, whose probe strings
start `python3 -I chaos/harness/reach.py`, and the harness fence
`ks-run-keeps-earlier-runs` with its two strings. Probe the harness fence as "Validate
the contract" says, from a shell that sets no `PYTHON*` variable, with `chaos/harness/`
holding its tracked files alone; its probe is the harness's dry run on an existing run
id, which starts no sweep. Start no run until each of those probes exits 0 and the
contract check, run again, reports no finding on a fence. Commit the new fence receipts
before the session's first run, so
the history of `chaos/receipts/fences/` keeps each session's refusals and their times
beside the runs they preceded.

Before a launch, run the harness with `--dry-run` for the run id and confirm that neither
`chaos/runs/<run-id>/` nor `chaos/receipts/<run-id>/` exists. Then start each run in its
own scope, a live run with no flag and a control run with the control's defect:

```sh
systemd-run --user --scope -p Delegate=yes --unit=chaos-<run-id> -- \
  bash <wrapper> <scenario-id> <run-id> [--control <defect>]
```

The harness refuses a run id whose directory exists under `chaos/runs/` or
`chaos/receipts/`, and `--dry-run` checks the scenario and the run id and starts
nothing. It exits with the run's result: 0 held, 1 broken, 2 invalid, 3 incomplete, and
2 for a refused argument. Read the verdict from the receipts this launch wrote, since the
launcher's exit can mean something else: `systemd-run` exits 1 when the scope does not
start, and the wrapper exits 1 when a setup step fails before `exec`, and neither writes
`chaos/receipts/<run-id>/`. The receipts count for this launch only when that directory
stood absent before it. The run's result reads the field `key.outcome` of every receipt
in it, the scenario row's and each listed invariant's: the run is broken when any
invariant's receipt says broken, held only when every receipt says held, and otherwise
undecided. The scenario row's receipt states the run's validity alone. A sweep of 120 s
with 28 workers takes about 123 s on this host, which takes one run at a time.

A run whose harness and judges have exited, and for which the validator reports
`run-without-receipts` or `incomplete-receipts`, is judged with each row's judge command,
for the scenario row and each invariant it lists. Create `chaos/receipts/<run-id>/`
only when it is absent, since the judge creates only the receipt file. Judge only the
rows whose receipt file is missing. The judge creates its receipt exclusively: at a
receipt path that exists it keeps the file as it is, prints no verdict and exits 2. Then
run the contract check, which shows whether it accepts the completed set:

```sh
[ -d chaos/receipts/<run-id> ] || mkdir chaos/receipts/<run-id>
python3 -I -B <judge script> <row> --evidence chaos/runs/<run-id> \
  --receipt chaos/receipts/<run-id>/<row>.json
```

## How a judge decides

The judges under `chaos/judges/core/` read only the evidence copies, and the
verdict mapping of [#297](https://github.com/ahrav/kestrike/issues/297) ("Verdict
mapping") defines each verdict. The module documentation of `validity.py` and
`invariant.py`, and in `common.py` beside them `Evidence.check`, `trusted`, `witnessed`,
`reached`, `validity` and `main`, state the conditions a verdict needs. In outline, the
validity judge `validity.py` finds a run valid when its records stand (the sweep's own
exit, no totals flag, the root's build equal to the archive's, the archive verified after
the sweep, no process left, no `replay differs` suspect), each profile of the scenario met
its witness minimum, has a replay and lists suspects of class violation only, each
cluster profile met the row's reach minimums, and the controls the root holds have runs
and at least one caught run.
The minimum counts `caught` for a history that
declares its failure, `covered` for a cluster profile and `pass` otherwise. In mode
`control` the named defect also has runs, a replay and no miss.

The invariant judge `invariant.py` reports broken only through its row's rule text,
`control.expect`. Both live paths below also match its obligation code,
`witness.obligation`, and the control path matches the text alone. The judge writes the
full text into the receipt's detail:

- in mode `live`, by a `violation` suspect key with the row's code and rule digest and a
  finding of `campaign confirm` for it, or by a history of the scenario whose listing
  declares the violation of the row's code and text and that counts caught runs under the
  text in `caught_rules`;
- in mode `control`, by caught runs of the named defect under the text.

A control the sweep ran unnamed never gives broken. A history that declares its
violation, such as `k9-placement-across-close` of the scenario `ks-escape-2075`, breaks
its invariant by the second path while its defect stands, and its control run names the
history's control, such as `k9-placement-judged-open`. Both live paths stand behind
`trusted`, which refuses a totals flag. Once such a history expects a pass, a completed
sweep in which it has at least 64 runs with no pass and no catch lists it under
`no_pass`, and both judges then return invalid. The flag alone shows no cause: the
history's `suspect_keys` and the findings of `campaign confirm` show it.

The outline above is the core judges'. The judges under `chaos/judges/reach/` decide the
scenario `ks-reach-required-events` and its invariant `ks-required-events-reached` by
rules of their own, which the module documentation of `reach.py`, `validity.py` and
`shared.py` there states. `campaign sweep` exits 1 when its totals carry `unreached` or
`no_pass`, and those two flags are the sweep's verdict on reach, which the invariant
judge `reach.py` decides. So the validity judge `validity.py` holds every run that
`sound` of `shared.py` accepts: a recorded sweep exit of 0, or of 1 with one of those two
flags, no `alarm` and no missed run, the records that `trusted` checks with the two flags
set aside, and each profile of the scenario with runs, a replay and suspects of class
violation only. The row's reach minimums and the covered-pass floor are the invariant
judge's to read, and neither reach judge asks for a caught control. A valid reach run can
therefore record a sweep exit of 1, as the control run `reach-control-1125b` does. The
invariant judge reads the two flags and each profile's `covered` and `reached` counts. It
reports broken when the sweep lists a profile of the scenario under `unreached` or
`no_pass`; held when the sweep exited 0 with neither flag and each profile has the row's
floor of covered passes and, for each event the required-event table requires of it, a
covered pass that reached the event; and incomplete when a profile is under that floor
and the status carries neither flag. Its control is the scenario's own sweep under the
campaign binary that the row's `control.how` states: it gives broken only when the sweep
lists the pair that the row's `control.defect` names, and it never holds. Every reach
receipt ends with the scope sentence of `chaos/project.yaml`.
`chaos/tests/test_reach.py` tests both judges, as
[the tests' README](../../chaos/tests/README.md) describes.

## When the receipts of record are made again

A receipt binds its verdict to the SHA-256 of each judge file, each harness file and each
evidence file, and to the digests of its row and its scenario row without their
statuses. A later change to a judge, the harness or one of those rows makes the receipt
stale, and the validator prints `stale-receipt` for it. A status change and a new row
leave earlier receipts valid. When such a change lands, the session of the unit that
owns the runs makes them again in the order below. A stale receipt counts for nothing and
keeps the validator's finding, and while any finding stands the validator renders no
claim and the pre-push check refuses a push that changes a path under `chaos/`. The
validator's messages for `run-without-receipts` and `row-changed-after-run` say to remove
or retire a run only with the owner. The validator enforces no approval, and it cannot
see a run whose evidence and receipts were removed together.

1. Before the commit that makes receipts stale, the session pushes a stop note under
   `chaos/loop/stops/`, from a tip that passes the contract check. The note names the
   change and each run id whose receipts the change makes stale. The owner's answer, or
   the answer of the person a recorded owner delegation names for it, names the pairs it
   lets the session retire. An answer under the sessions' shared GitHub login counts only
   when the owner confirms it outside the sessions, as "What the driver provides and
   lacks" states.

   A step that meets a commit that retires a run and receipt pair, or that makes a
   receipt stale, pushes the stop note first and waits for the answer of the party the
   recorded delegation names, before the commit. The confirmations of 25 November 2026
   accept a stop note written after its commit for the commits that
   `chaos/loop/stops/remakes-after-the-record.md`,
   `chaos/loop/stops/record-retirement.md` and
   `chaos/loop/stops/merge-of-start-c05.md` name, and for no later one.
2. With that answer, the session commits the change and makes the live and control runs
   again under new run ids, on one archive built at its branch's head. For a row change
   that comes with a fix of the cache, the live and control runs on the unfixed archive
   come first, under the amended row, so that a usable broken run of an earlier build
   stands for `fixed`; the runs of the fixed archive follow. One archive serves the live
   run and every control that selects a profile. A control whose row's `control.how`
   states a changed archive or a changed campaign binary sweeps that build: it is made
   from the same commit as the live run's archive and binary, in a scratch copy that
   holds the `Cargo.lock` of the live build, with `--locked` for a binary, so that the
   change the row states is the one difference in its inputs. The session's dated note in
   `chaos/loop/log.md` names that commit and the digest of each archive and binary, since
   `control.how` of `ks-required-events-reached` points to that note for the commit and
   `run.json` records a binary by its SHA-256 alone. A later campaign that keeps its own
   log under `chaos/loop/<campaign>/` writes the note in `chaos/loop/log.md` as well.
3. In the commit that adds the replacements, the session removes the approved stale run
   and receipt directories, renders the claim once, and runs `--check-claim` on that tree
   before the push.

Without the answer, the session keeps the stale records, pushes no tip that holds a stale
receipt, and waits. The live and control runs of each invariant are what the validator asks
for: `witness-missing` and `control-missing` name a row that lacks them.

## The chaos loop

The chaos loop works the frozen contract: a coordinator session runs the contract
check, picks a scenario, runs it, reads the receipts, has each break audited by a worker
with its own context, and writes a stop note for each change that stops for the owner,
until a stated end. It follows the skill `chaos-loop` of plugin `chaos-testing`, and its
rules come from the briefs that skill renders.

### Render the briefs

Run the render from the repository root, with the installed skill's script, the pinned
validator, the freeze commit's full id and the tool text, into a directory outside the
checkout:

```sh
python3 <chaos-loop skill>/scripts/render_loop.py --ledger chaos/ledger.json \
  --project chaos/project.yaml --freeze-commit <freeze id> \
  --tools chaos/loop/driver-tools.txt --validator chaos/tools/validate_contract.py \
  --out <directory outside the checkout>
```

It runs the validator with `--freeze-commit` first and renders only a ready contract.
Exit 0 prints the SHA-256 of `run-rules.md`, `coordinator-prompt.md` and
`worker-prompt.md`; exit 1 lists what the contract lacks; exit 2 names an input to
correct. On exit 1 or 2 start no coordinator: correct the input the render names, and
take a gap in the contract after the freeze to the owner or the workstream's lead. The
three files stay uncommitted, and the final report records their digests.
The render needs a budget that limits the whole campaign written as its own clause, such
as "12 runs for the whole campaign", in `budgets` of `chaos/project.yaml`.

`chaos/loop/driver-tools.txt` is the rehearsal's tool text, the input whose SHA-256
`chaos/loop/final-report.md` records, and it stays as that render read it. It names the
rehearsal's checkout, archive, `campaign` binary, build, roots and brief directory, and the
render copies it into both prompts unchanged. A later campaign writes its own tool text
at `chaos/loop/<campaign>/driver-tools.txt`, where `<campaign>` is a new name in the form of
a run id. That text names the campaign's own checkout, archive, binary, build, roots and
brief directory, the `--out` directory of its render. It puts every record path it names
(the log a hold stands in, findings, audit reports and the final report) under
`chaos/loop/<campaign>/`. It states each procedure in this guide's words. The rehearsal's
text is older than parts of this guide: the fence check before a run on another worker
and the probe of the harness fence ("Run a scenario"), the owner's answer to A1 before a
sweep, and the second hold check before the rules read `held` ("Statuses"). So a later
campaign takes each procedure from this guide. The campaign
renders with that file and its directory:

```sh
python3 <chaos-loop skill>/scripts/render_loop.py --ledger chaos/ledger.json \
  --project chaos/project.yaml --freeze-commit <freeze id> \
  --tools chaos/loop/<campaign>/driver-tools.txt --loop-dir chaos/loop/<campaign>/ \
  --validator chaos/tools/validate_contract.py --out <directory outside the checkout>
```

Then it starts a new coordinator session. `chaos/approval-policy.md`, a frozen path, names
`chaos/loop/stops/` for stop notes, and `--loop-dir` moves the rendered rules' stop notes
to `chaos/loop/<campaign>/stops/`; which of the two a later campaign uses is the owner's
to settle at the next freeze.

### What the driver provides and lacks

`chaos/loop/driver-tools.txt` is the rehearsal's tool text. It states the nine items the skill's
driver handoff asks for: what the sessions read and write and as whom, how a run starts
and how many run at once, how a change reaches the copy and how the build digest is
read, the validator and the probe command, who sets a status, where stop notes and
findings go, where the claim and the final report are written, the telemetry, and how
the coordinator starts a worker.

| The rules assume | On this host |
| --- | --- |
| The harness, the judges, the receipts and the rendered briefs are out of the sessions' reach | Lacking. One Unix user runs the sessions and the harness and can write every frozen path, `chaos/runs/` and `chaos/receipts/`. The contract check with the freeze id compares the frozen paths with the freeze commit and each ledger row's frozen fields with the freeze's rows, so it finds an edit to them after the fact. Under `chaos/runs/` and `chaos/receipts/` it checks only that the records present agree: the evidence with the digests its receipts name, each receipt with its row, judges and harness, and each run directory with its receipt directory. It reads each receipt's outcome as written, reruns no judge, and cannot see a run whose evidence and receipts were both removed. The rendered briefs stand outside the checkout, writable by the same user; the digests the final report records find a change to them |
| A run started the loop's way | The harness in a delegated scope, as "Run a scenario" above shows; one run at a time |
| A probe command that records a fence's receipt | `python3 <skill-dir>/scripts/probe_fence.py chaos/ledger.json <fence-id>`, with the skill `chaos-enrollment`, run as the campaign's user |
| A worker with its own context, and the audit skill where it runs | The agent host's sub-agent tool, a general-purpose agent that starts with `worker-prompt.md`, the path of `run-rules.md` and its one item; the plugin `chaos-testing` is installed |

| The rules read again after a compaction | Lacking: no project-root pointer or session-start hook names `run-rules.md`. The coordinator reads the file again at each iteration, as rule 10 asks |
| A cap on spend and a wall-clock limit | The rehearsal budget in `budgets` of `chaos/project.yaml`, counted by the coordinator; no cap below the session enforces it |
| A status set by a named session | During the rehearsal the coordinator sets `status` and commits it; after the freeze, a status of `held` or `fixed` is set as a record by a pull request and its merge into `main`, as "Statuses" and the ruling on OQ-1 state (`chaos/interview.md`, "Ruled for the owner").
